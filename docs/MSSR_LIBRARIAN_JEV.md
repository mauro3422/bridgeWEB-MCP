# MSSR Librarian and Jev in Bridge

Bridge integrates the Librarian and semantic-evidence workflow through six MCP tools backed by the versioned `@mauroprime/mssr` package. Live Bridge 0.6.159 uses the locally release-gated MSSR 0.2.108 artifact (SHA-256 `8478731d2c653e50b2a5718f4fe5b30b3b40f8ddc99df67163b8c9a9b72b9f21`). MSSR owns deterministic retrieval, revision-bound handles, EvidenceAtom validation, Jev selection/relation contracts, reversible synthesis previews, exact-heading projection, exact-citation evidence-pack construction, and fetchable-range tie ordering. Bridge owns project-root authorization, bounded canonical manifest and Markdown reads, source/manifest freshness checks, provider transport, and Windows Credential Manager access. Controlled watchdog restart and live readback verified Bridge 0.6.159, 186 tools, and ready local/tunnel endpoints. The current health contract does not expose the loaded MSSR version/hash directly; package identity is established from exact release artifact parity and the tested adoption path.

For a capability-by-capability inventory of 100 current, partial, and proposed decision cases, see [MSSR_JEV_USE_CASE_CATALOG.md](MSSR_JEV_USE_CASE_CATALOG.md). The catalog is an evaluation roadmap, not an implementation claim.

## Capabilities

- `mssr_librarian_search` searches only explicit project-relative Markdown `sourceRefs`. It defaults to deterministic lexical matching. Metadata is opt-in and supports two modes: the legacy `project-context-single-section` mode derives selectors from one unique heading declared by a selected `context`, `memory`, or `state` module in `.mssr/project-context.json`; the new `project-context-librarian-sidecar` mode uses individually declared exact headings in `.mssr/project-context-librarian.json`. The sidecar projector checks entry IDs and source paths against the canonical context manifest, rejects directive and segment/reference-bound modules, requires the exact heading path and current Markdown fingerprint, and enforces any source-section boundary. It does not inherit broad module selectors or infer tags from prose. Both modes process only the explicit `sourceRefs`, return revision-bound section/block handles, and leave metadata advisory. The new mode reports declaration/projection/omission details and hashes for the canonical context, librarian, segment and reference manifests. A missing librarian sidecar or a changed input falls back to lexical-only results with an explicit status; invalid or unsafe project-control files fail closed. Each range reports UTF-16 size and exact-fetchability under the 20,000-unit cap. Neither mode persists an index or crawls runtime stores.
- `mssr_librarian_jev_select` makes a live Jev choice. It can use heading candidates or up to 100 exact handles returned by `mssr_librarian_search`. For metadata-assisted retrieval, call search with the opt-in mode and pass its exact handles to Jev selection; the two steps stay separately inspectable. MSSR revalidates owner, explicit source, privacy class, revision, range, and fingerprint before the provider call, then omits ranges the exact-fetch API cannot return whole. It reports offered/eligible/oversized counts and read-only range-overlap diagnostics for supplied sections/handles; those diagnostics describe nested/duplicate alternatives and never merge ranges or alter candidates. When no range is fetchable it returns `not-run` without a Jev call, distinct from Jev abstention. The result is only a selected handle; fetch it before using source text.
- `mssr_librarian_fetch` rereads the selected Markdown file and rejects stale handles or ranges whose revision/fingerprint changed.
- `mssr_librarian_evidence_pack` rereads only explicit canonical Markdown sources and packages validated, revision-bound handles into a citation-preserving evidence object. It requires exact owner/privacy/source agreement, rejects duplicates and stale/tampered handles, and returns the selected source ranges in caller-specified order. It does not ask Jev, infer relevance, summarize, generate prose, or write files. This restores a capability that existed in Bridge 0.6.148 and was lost in the later 0.6.154 lineage; it is not a second differently named tool.
- `mssr_semantic_evidence_relation_review` rereads cited ranges, ignores caller-supplied replacement text, and asks Jev for bounded typed relations such as supports, contradicts, supersedes, duplicate, unrelated, or unresolved. Judgments remain unverified and advisory; raw confidence is uncalibrated.
- `mssr_semantic_evidence_synthesis_preview` rereads exact sources and creates an immutable, relation-aware preview. The text is assembled from source ranges; it does not generate new paragraphs or perform generative compaction. Conflicts, stale evidence, unverified judgments, or unknown comparability remain review-only. Bridge never applies the preview to project files.

The composed workflow is explicit retrieval → Jev selection (when requested) → exact fetch or evidence-pack construction → typed relation review → optional reversible preview → independent host verification. Jev does not search beyond the host-supplied corpus, establish truth, grant permissions, execute tools, or write files. The host may iterate bounded searches, select candidates, compact evidence to exact cited ranges, assemble answer paragraphs, review contradictions, and verify every claim; these remain observable orchestration and generation stages around Jev. The evidence-pack `paragraphs` are verbatim source excerpts, while answer paragraphs are composed by the host and must carry exact citations. Bridge's current synthesis preview deterministically assembles exact source ranges; it does not generate or compact prose. The six registered Bridge tools cover bounded retrieval, selection, exact evidence, citation-preserving evidence packs, typed relations, and a reversible source preview. The evidence-pack tool restores the earlier 0.6.148 capability; this candidate does not introduce a duplicate MCP tool.

For the executable host-side sequence—including query coverage, bounded follow-up retrieval, statement-level citations, contradiction handling, and safe resumption—use the project-scoped [MSSR Librarian and Jev Evidence Composition workflow](../.bridge/workflow-guides/mssr-librarian-jev-composition/GUIDE.md). Load its phases when a task asks the host to investigate project documents or prepare a citation-grounded synthesis.

## EvidenceAtom ingress boundary

The portable MSSR search contract accepts optional EvidenceAtoms and catalog records. Their projected metadata can affect matching only when the atom, its catalog-record binding, canonical owner, explicit source reference, current revision, exact source range, payload/record fingerprints, and privacy class all agree with the Document Surface derived from the current Markdown. MSSR exposes only a closed vocabulary of matched fields and labels provenance caller-asserted; this is useful evidence, not authentication or authority.

Bridge has two on-demand metadata producers. The legacy single-section path derives records and EvidenceAtoms from eligible one-heading `context`/`memory`/`state` modules in the canonical project-context manifest. The new MSSR 0.2.101 sidecar path derives them from owner-declared heading entries in `.mssr/project-context-librarian.json`. Both receive only caller-selected Markdown bytes. The sidecar path also reads the canonical optional segment and reference manifests within `.mssr/`; these only suppress overlapping projections and never add Markdown sources. The host rechecks all manifest revisions and canonical paths after projection, then returns lexical-only results if any input changed. Sidecar declarations must match a current base-manifest entry, selected source path, unique heading path, current heading fingerprint, and any enclosing source-section scope. It rejects directives and modules already represented by segments or references. Projector status, manifest hashes, per-entry omissions and exact entry-to-range bindings are returned for review; records and atoms are not stored persistently. The sidecar projector marks atom freshness `unknown`; a current source fingerprint supports exact binding, not authorship or truth.

The sidecar accepts only declared `domains`, `actions`, `artifacts`, `needs`, and `signals` for each exact heading. It does not use module-wide `topic`, `area`, prose, or terms as selectors. MSSR's projector rejects missing/stale/ambiguous headings, stale fingerprints, out-of-scope bindings, unknown entries, and duplicate or unsafe declarations. Bridge caps the librarian sidecar at the portable 2 MB limit and optional project-context sidecars at 1 MB each; total Markdown reads stay within 4 MB / 32 explicitly selected files, and all projected record/atom counts are checked against the packaged retrieval limits. The legacy path reports `limits-exceeded` if its projection is too large; the sidecar path likewise discards the complete projection. These per-call producers create no catalog or telemetry store. Runtime telemetry, caller-supplied atoms, and relation-review inputs are not Librarian metadata sources.

## Source and privacy boundary

Each call requires a Git project root containing the canonical `.mssr/project-context.json`. Sources must be explicit, project-relative UTF-8 Markdown paths. Bridge caps each source at 2 MB, each batch at 4 MB and 32 files, and each semantic operation at the packaged MSSR limits. It validates the resolved canonical target as well as the requested path, so an internal symlink or junction cannot alias `data/`, `logs/`, `.git/`, `.bridge/`, `node_modules/`, `.mssr/runtime/`, or sensitive-looking paths. Absolute paths, traversal, and colon-containing paths (including Windows Alternate Data Streams) are rejected.

Live Jev selection and relation review may incur account usage. On Windows, Bridge reads the `TypeSafe:MSSR:JevLab` credential from Windows Credential Manager on demand through `scripts/read-windows-credential.ps1`. `BRIDGE_MSSR_JEV_CREDENTIAL_TARGET` can select a different target and `BRIDGE_MSSR_JEV_MODEL` can select a model. The API endpoint is pinned to `https://api.typesafe.ai`; inherited `TYPESAFE_BASE_URL` configuration cannot redirect the credential. The API key is not accepted in MCP arguments, copied to an environment file, logged, or placed in telemetry. If the credential is absent, a Jev operation fails with a generic unavailable message; other Bridge tools remain available.

When the Windows trust store accepts the provider certificate but Node's bundled roots do not, launch the Bridge Node process with `--use-system-ca` (or `NODE_USE_SYSTEM_CA=1`). This adds operating-system trusted roots while preserving normal TLS certificate validation; it does not disable verification. The managed Windows HTTP watchdog now sets the variable only on its spawned Bridge child; it does not change user- or machine-level environment. Verify the actual Bridge launch environment before expecting Jev calls to work. Node documents the environment option as available in v24.6.0/v22.19.0 and equivalent to `--use-system-ca` ([Node.js CLI docs](https://nodejs.org/api/cli.html#node_use_system_ca1)).

## Evaluation evidence and limits

### Full-heading benchmark (2026-09-30; separate MSSR harness)

The paired run used 21 tracked MSSR documents, 26 English/Spanish query pairs, 200 headings and 505 non-heading blocks. The same Jev provider was offered either the deterministic top-100 shortlist or all 200 headings plus none (201 options). Exact expected-heading selection was 15/52 (28.8%) from the shortlist and 34/52 (65.4%) from the full catalog: English 12/26 to 18/26 and Spanish 3/26 to 16/26. Full-catalog selection added 22 hits and lost 3 cases versus the shortlist. Exact fetch passed 48/48 full-catalog selections; the shortlist passed 32/33, with one 20,000 UTF-16-code-unit cap rejection and no integrity failures.

The full-catalog calls used 829,804 input / 105,392 output tokens and averaged 409 ms; the top-100 run used 501,232 / 53,347 tokens and averaged 375.5 ms. This is a promising candidate-recall signal in a small, document-visible set, not unseen-document generalization: the same 21 documents remained visible, target labels were double-reviewed but not approved by the document owner, and the 505 body blocks were not offered individually. It suggests fixing retrieval recall before tuning confidence cutoffs and measuring any hierarchical candidate strategy against the provider's finite choice limit. The frozen report and artifacts are under D:\Dev\mssr\experiments\jev-mssr-live\runs\mssr-librarian-jev-full-heading-choice-20260930-v1\.

### Live Bridge exact-handle smoke (2026-10-01)

The live Bridge 0.6.144 / MSSR 0.2.96 run made three Jev calls over real MSSR documents. Jev selected the author-preferred exact handle in 3/3 cases; exact fetch passed 3/3, with no abstentions or provider failures. Usage was 2,371 input / 171 output tokens and mean latency 777.2 ms. Blind review found all selected evidence useful and noted overlapping equivalent ranges. One useful selection had provider score 0.42 and was independently judged correct; this rejects treating 0.5 as a safe default cutoff. Scores remain uncalibrated. ## Decision-only models and external evidence

The useful system pattern is a typed decision inside a larger, code-owned workflow. TypeSafe's launch post describes Jev as accepting state and returning typed probabilistic decisions; claims about speed, cost, calibration, and performance are vendor claims that need validation on our own corpus. The Bridge path follows that separation: code constructs and fetches candidates, Jev selects or labels a bounded choice, then exact-source checks and a separate verifier retain authority.

An independent September 2026 Entagl evaluation used 283 labeled cases across 13 decision tasks (1,357 scored decisions) and replayed 402 routing decisions from two workspaces. It reports 98.5% vs. 99.0% accuracy in the labeled set and a faster median response for Jev, but the real-workspace review used one reviewer, excluded unclear cases, and oversampled rare outcomes. Its reported confidence bins were useful on that data, yet it also reports a repeated 0.95-confidence error. These results are evidence that task-specific confidence and fallback tests are worth running; neither the accuracy nor an 85%/97% threshold transfers to MSSR. A Reddit router post describes prefetching, choosing subpages to crawl, and place deduplication, but its author explicitly calls the two examples exploratory rather than an evaluation.

OpenAI's September 29, 2026 DevDay recap describes Decisions API as limited preview: Luna answers finite user-defined questions from text or image context for classification, routing, or selecting an agent's next action. The recap does not provide the API schema, pricing, calibration evidence, or comparable MSSR results. It is directionally similar to Jev's bounded decision role, but should be benchmarked separately when access and its technical contract are available. Its stated image input is a modality distinction from the current text/evidence-based Jev calls. For a valid comparison, freeze candidate sets and gold labels before calls, then report retrieval recall, selector accuracy conditional on a correct candidate being present, abstention/coverage, confidence calibration, exact-fetch integrity, and end-to-end answer quality separately.

Sources: [TypeSafe launch and vendor claims](https://typesafe.ai/blog/introducing-system-one-models-and-jev), [independent Entagl evaluation and method](https://www.entagl.com/blog/typesafe-jev-benchmark-ai-decision-models), [OpenAI DevDay 2026 announcement](https://openai.com/index/devday-2026-recap/), [exploratory Reddit router examples](https://www.reddit.com/r/LLMDevs/comments/1wihigc/tried_typesafes_new_decisiononly_model_jev_as_an/).

## Ignored runtime data

`data/` and `logs/` remain outside Git and protected from this Librarian adapter. A historical metadata-only inventory of the Bridge checkout found 10,675 files totaling about 1.69 GB. Jev reviewed only an aggregated, path-free summary against the repository's preserve-by-default rule: preserving/classifying was supported, deletion contradicted the rule, and the inventory alone did not justify deletion. Those answers are unverified guidance; no file-level retention or deletion decision follows from them.

Use deterministic cache/storage tools and explicit owner, activity, freshness, and regeneration evidence to review runtime data. Keep protected stores unless their owning policy authorizes bounded pruning. Never treat Jev confidence as a deletion threshold or as permission to mutate canonical data.
