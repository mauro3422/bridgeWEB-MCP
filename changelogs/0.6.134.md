# 0.6.134 — 2026-09-18

- Summary: make the existing Bridge notice transport contextual and low-noise without creating another notice system: current project/trace attention is delivered preferentially, unrelated project attention is count-only, and the global 24-hour history remains explicitly recoverable.
- Areas: notices, MCP response delivery, MSSR relay lifecycle, background work lifecycle, persistence/restart reconciliation, tests, project knowledge
- PROJECT_CONTEXT: updated indexed notice-history authority only
- PROJECT_MEMORY: reviewed-none
- PROJECT_STATE: updated

## Changes

- `bridgeNotices` remains the only general Bridge notice transport. A host-side delivery policy now derives bounded relevance from the active `traceId`, project and workflow; exact trace attention wins, then project/workflow attention, while unrelated scoped notices stay out of the active response body and are represented by `otherPending` counts.
- Ordinary MCP responses deliver at most two notice bodies and expose `relevantPending`, `otherPending`, `globalPending`, plus `globalHistoryTool=bridge_notice_history`. Unscoped warnings/errors remain eligible as global operational attention.
- The pending queue now models current unresolved attention rather than every historical transition. Genuine MSSR wrappers use the preserved `MssrNotice.noticeId` only as a host-side lifecycle grouping key: a changed unresolved transition supersedes the previous pending wrapper; `resolved` / `attentionLevel=ok` clears it while the full transition remains in history.
- Exact MSSR semantic transitions already delivered once remain quiet until their semantic event/fingerprint changes. Native Bridge failures retain recurrence behavior.
- Informational `mssr-context-message-v1` notices and successful terminal/job lifecycle events are history-only. Terminal/job warnings remain active until a resume/success lifecycle signal clears them.
- Automatic draining no longer has FIFO head-of-line blocking. It scans eligible candidates, can emit a compact host-only summary for an oversized wrapper, and can bypass a candidate that cannot fit an exceptionally small residual budget without blocking later bounded notices. Full stored notice/history data is not compacted or rewritten.
- Notice persistence restores through the same lifecycle reconciliation, so a pre-0.6.134 persisted `started/stalled/resumed` or equivalent resolved chain cannot become fresh pending attention after restart.
- Automatic metric notices now carry bounded host `traceId` / project / workflow scope when available so failures, latency, and large-output attention can be routed to the active context without changing their native semantics.
- Corrected project state: notice-history was not owned by another concurrent workstream; it is part of the Bridge/MSSR notice subsystem and is maintained here.
