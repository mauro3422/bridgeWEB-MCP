# 0.6.106 — 2026-08-17

- Summary: Operational Notice Plane Gate E3 Bridge adoption on packaged MSSR 0.2.31. Genuine `MssrNotice v1` payloads are now preserved as a separate validated semantic object through the existing Bridge queue/history/automatic-drain transport while Bridge-owned delivery metadata and actions remain outside the portable payload. Foreign/native Bridge notices remain foreign/native and are not relabeled as MSSR.

## Changes

- Vendored verified MSSR `0.2.31` tarball (`480919` bytes, SHA-256 `c97e51924b39ec2d2d3f84a38039e89906c842cf2782bb2165d340e18ac95b70`) and changed Bridge dependency from packaged MSSR 0.2.26 to 0.2.31.
- `BridgeNoticeInput` / `BridgeNotice` now optionally carry `mssrNotice` only for a genuine validated portable notice. Existing Bridge queue ids, TTL/timestamps, occurrences, history, host details and suggested actions remain host delivery metadata.
- `adaptMssrOperationalDecision(...)` no longer treats the portable candidate as a bag of fields to merge with host details. It validates the `MssrNotice v1`, embeds it intact, and derives compatibility mirrors from that preserved object.
- Queue peek/drain/emit return a revalidated semantic clone so a caller cannot mutate the portable payload retained internally by the Bridge queue.
- Existing `bridgeNotices` remains the only general notice queue. Gate E3 adds no second MSSR queue, sink, spool or scheduler.
- Native Bridge/foreign MCP notices continue through the same transport without `mssrNotice`; E3 never normalizes or relabels them as MSSR.
- Added `scripts/test-mssr-notice-relay.mjs` and aggregate regression coverage for semantic parity across Bridge wrapping, queueing and draining; host metadata exclusion; semantic-id versus delivery-id separation; returned-clone isolation; one shared Bridge queue; and foreign-notice identity preservation.
- Bridge version moves to 0.6.106. No new MCP tool is introduced; the expected live catalog remains 156 tools.
