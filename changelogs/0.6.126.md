# 0.6.126 — 2026-09-16

- Summary: Stabilize ChatGPT Web Bridge transport under multi-chat concurrency by hardening HTTP keep-alive, removing synchronous filesystem pressure from hot paths, honoring the no-guide context fast path, and preventing the watchdog from killing an alive runtime during transient readiness stalls.
- Areas: HTTP/MCP transport, tunnel diagnostics, watchdog recovery, filesystem path policy, skill/context loading, runtime observability, regression coverage
- PROJECT_CONTEXT: reviewed-none
- PROJECT_MEMORY: reviewed-none
- PROJECT_STATE: updated

## Changes

- Bridge HTTP now advertises a 120-second keep-alive window, uses a 5-second keep-alive timeout buffer, and keeps headers timeout above that combined window. This avoids stale pooled-socket reuse races between `tunnel-client` and Node HTTP.
- `/status` exposes bounded event-loop lag/stall diagnostics, HTTP client-error counters, session-not-found counts, and the active HTTP timeout contract for incident correlation.
- `tunnel_health` / `bridge_health` parse bounded tunnel Prometheus metrics and correlate tunnel-service 502 responses with local `POST /mcp` attempts that received no HTTP status. A per-tunnel-process baseline exposes only deltas for new incidents.
- Filesystem navigation/writing and Codex skill discovery reuse prepared async path-policy validation instead of repeatedly performing synchronous canonical-path resolution on the HTTP event loop. Symlink, denied-root, and canonical-boundary enforcement remain unchanged.
- `project_context_load(includeGuides=false)` now skips workflow-guide recommendation entirely rather than only skipping guide discovery.
- The HTTP watchdog still restarts immediately when the Bridge process has exited. If the process is alive, readiness failure must now satisfy both the consecutive-failure threshold and a 90-second sustained degradation grace window before recovery is allowed.
- Before an alive-process readiness recovery, the watchdog records bounded `/status` evidence including runtime boot, event-loop diagnostics, session lifecycle, failure age, and grace duration.
- Regression coverage now protects long keep-alive headers, transport-metric aggregation, runtime diagnostics, the no-guide fast path, and the sustained-readiness watchdog contract.

## Incident evidence

- During the audit, ChatGPT Web calls reproduced `Connection failed` while the Bridge process retained the same PID/boot. Tunnel debug evidence showed `initialize` failing with `wsarecv: An existing connection was forcibly closed by the remote host` while forwarding to `127.0.0.1:3001/mcp`.
- Tunnel counters correlated exactly: tunnel-service 502 totals matched local `POST /mcp` requests with no returned HTTP status. This separated upstream socket failure from a tool-level error or reclaimed MCP session.
- A second failure mode was also reproduced: multi-second event-loop stalls caused the old watchdog policy to issue `auto-restart-http-readiness-threshold` even though the Node process was still alive, creating real reconnect/502 windows for concurrent chats.
- The live pre-fix server advertised `Keep-Alive: timeout=5`. Event-loop instrumentation observed stalls up to roughly 16.7 seconds during the investigation, including expensive context/skill discovery and synchronous path-policy work.
