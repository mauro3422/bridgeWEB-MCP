## Root causes

- `skill_bootstrap`/`skill_route_plan` discovered the local skill catalog and later workflow-guide ownership coverage could rediscover the same catalog in the same operation.
- Repeated calls rescanned and revalidated the Codex skill roots even when no skill changed. The deterministic MSSR route itself was comparatively small once discovery was warm.
- Remaining warm latency came mostly from synchronous observability receipts. `mssr_events` and `tool_calls` share the metrics SQLite store; normal inserts remained bounded, but SQLite WAL autocheckpoint work could land on a routing commit and add tens of milliseconds to each receipt.
- Adding detailed timing to compact bootstraps initially exceeded an existing 18,000-character pagination envelope; timing therefore also needs to obey the same outer response budget as routed context.

## Changes

- Reuses the already discovered skill catalog when workflow-guide ownership checks existing skill coverage inside the same route/bootstrap call.
- Adds a watched in-memory Codex skill catalog for `~/.codex/skills` and `~/.codex/plugins/cache`, with recursive change invalidation where supported and a bounded 30-second TTL fallback. Cold scans remain authoritative; warm calls avoid rereading unchanged skill files.
- Adds `BridgeTimingCollector` envelopes with `totalMs`, `instrumentedMs`, `uninstrumentedMs`, runtime boot identity and per-phase durations. `skill_bootstrap` now exposes routing, guide resolution, context planning, selection and observability costs separately.
- When a compact bootstrap cannot fit the full timing phase array, it emits a compatible compact timing summary with `phaseDurationsMs` instead of enlarging the context envelope or dropping routed obligations.
- Adds Bridge dispatch metadata for routing/context calls under `bridgeMeta.latency`, explicitly excluding caller-to-Bridge ingress and Bridge-to-caller egress.
- Adds the Bridge-native `bridge-routing-latency` notice at a routing-specific default threshold of 1,500 ms, preserving MSSR semantic notice ownership.
- Keeps JSONL and SQLite receipts synchronous, but disables SQLite `wal_autocheckpoint` on Bridge writers and schedules `PRAGMA wal_checkpoint(PASSIVE)` in a debounced worker. Checkpoint status is exposed through metrics status; a busy reader can defer maintenance without blocking MCP routing.
- Adds focused routing-latency and metrics-WAL-maintenance regressions and includes them in `verify-all`.

## Measured evidence

- A raw Codex catalog scan measured roughly 0.8–2.9 seconds depending on filesystem state; after watched cache warm-up, discovery measured about 2–4 ms.
- Existing-skill coverage fell from roughly 0.85–0.98 seconds to about 7–18 ms on warm calls.
- A profiled warm bootstrap identified deterministic routing around 11–16 ms, workflow-guide ownership around 13–18 ms and context planning around 1–4 ms; the previously unexplained gap was synchronous observability persistence.
- Before draining the live WAL, route/load receipts measured about 33 ms each. A passive checkpoint reduced the same real-store receipt phases to about 4.1–4.2 ms each and the measured warm bootstrap to 43.98 ms in that run.
- Focused regression after the worker/checkpoint change: cold bootstrap 944–999 ms, warm bootstrap 66–102 ms, warm skill discovery 2–3 ms, and less than 1 ms uninstrumented time.
- Isolated WAL-worker regression: one passive checkpoint completed with `busy=0`, checkpointed all pending fixture frames, and no worker failure while the checkpoint duration stayed outside the routing request path.
