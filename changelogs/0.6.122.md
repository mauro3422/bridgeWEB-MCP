# 0.6.122 — 2026-09-15/16

## Summary

Add bounded persistence-latency attribution for MSSR receipts so residual Bridge routing jitter can be diagnosed from the live HTTP process without enlarging routing/context envelopes or weakening synchronous evidence persistence.

## Changes

- `src/mssr-observatory.ts`
  - profiles each local MSSR receipt across event construction, JSONL append, database acquisition, SQLite insert, and WAL-maintenance scheduling;
  - keeps only a bounded in-memory ring of the latest timings;
  - exposes that ring only through explicit `mssr_observatory_query(kind=status)` diagnostics;
  - stores no raw prompts, transcripts, private reasoning, or tool arguments in this timing surface.
- `src/tools/skill-catalog-tools.ts`
  - adds `observability.route` timing to `skill_route_plan`, closing a previously uninstrumented persistence gap.
- `scripts/test-routing-latency.mjs`
  - requires `observability.route` in the route-plan timing contract.

## Diagnostic evidence

- Real `bridge-metrics.sqlite` is approximately 197 MB with ~119,769 `tool_calls` and ~25,524 `mssr_events` at investigation time.
- Direct `recordMssrRoute` profiling against the real store showed one cold-ish insert around 50–60 ms while subsequent inserts in the same process were typically ~1.5–3.6 ms; JSONL and scheduling were sub-millisecond to low-single-millisecond contributors.
- Synthetic WAL tests showed that `PASSIVE`, `RESTART`, and `TRUNCATE` checkpoints can each cost ~200+ ms as maintenance while the first subsequent write remained only ~3–4 ms. This rejects the earlier hypothesis that WAL-cycle reset alone explains the larger live insert jitter.
- Process/PID evidence showed the current HTTP Bridge as the only observed recent writer among the inspected Bridge PIDs; older stdio Bridge processes were not proven to be active contenders and were left untouched.
