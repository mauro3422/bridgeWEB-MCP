# 0.6.124 — 2026-09-16

- Summary: Make Bridge background work observable before termination and keep observability from starving the HTTP/MCP transport: attention deadlines are separate from hard timeouts, durable MSSR/metric persistence runs through a single-writer worker with immediate overlay reads, and WAL maintenance is deferred outside request work.
- Areas: process tools, bridge verify workflow, process-tree diagnostics, observability persistence, SQLite/WAL liveness, routing latency attribution, Operational Notice Plane, regression coverage, project knowledge

## Changes

- `work_begin` now defaults `timeoutAction=observe`: crossing its deadline marks the session `timed-out-alive`, emits a Bridge-native warning, and leaves the exact process tree alive for `work_peek` inspection.
- `terminal_start` preserves backward-compatible `timeoutAction=terminate` by default; callers may explicitly select `observe`.
- `bridge_verify_all` also defaults to `timeoutAction=observe`; hard termination is explicit.
- `work_peek` / `terminal_read` deep-inspect one exact session and return state/activity, output byte/line counters, last observed progress, and a bounded process-tree summary with aggregate CPU and working set.
- `work_show` / `terminal_list` remain lightweight and do not scan every process tree.
- Process inspection never returns raw command lines. It exposes only bounded PID/parent/name/resource data plus sanitized activity hints.
- Windows tree termination remains explicit and uses process-tree termination rather than a root-only signal.
- Bridge-native notices distinguish timeout-alive, timeout-terminating, stalled, and resumed progress without creating MSSR semantic notices for host process state.
- MSSR/metrics durability now leaves the request path: a shared single-writer worker persists bounded events while an in-memory overlay provides immediate read-your-writes semantics for live `trace`, `recent`, coverage and routing projections.
- SQLite WAL maintenance is isolated from receipt durability and runs with passive checkpoints after a true quiet-period debounce; new writes defer the next maintenance pass instead of forcing checkpoint work into the MCP/HTTP event loop.
- Routing latency is attributed by layer. Bridge exposes dispatch/phase timing and emits Bridge-native `bridge-routing-latency` attention when the interactive routing threshold is exceeded; transport/readiness/latency notices do not become MSSR semantic notices.
- Regression fixtures that own observatory/metrics/skill-discovery resources now close those resources explicitly before Windows sandbox cleanup, avoiding post-success `EPERM` failures that previously obscured functional results.

## Incident evidence

- A prior full verification crossed its 10-minute timeout while a descendant `test-delegated-mssr-route-project.mjs` process remained alive. The old root-only timeout path did not establish tree termination on Windows.
- The descendant later survived an HTTP runtime restart because the in-memory verify-job registry was lost; its exact regressions ancestry was reconstructed before terminating only that orphan tree.
- The isolated delegated-routing regression subsequently passed in about four seconds, so the fixture itself is not treated as the demonstrated root cause of the earlier long run.
- Repeated HTTP readiness restarts/502s were reproduced independently of the original orphan and traced to observability work competing with the shared HTTP/MCP event loop. The 0.6.124 async persistence + bounded overlay + deferred WAL maintenance path closes that incident; the final full regression and live post-restart smoke remained healthy.
