# Bridge skill-context and host routing contracts

## Resumable skill-context invariant

`maxContextChars` bounds selected procedural text while `maxEnvelopeChars` bounds the complete compact response (32.000 by default); neither may be inferred from the other. When selected context does not fit, `skill_bootstrap`/`skill_context_next` must expose a deterministic partial chain and the caller must reach `status=complete` before dependent work. Opaque cursors contain no prompt, transcript or procedural content, are valid only against the same trace/live selected bytes and order, and are kept only as a fingerprinted RAM continuation lease. R3 retention is explicit: suppress re-delivery only for caller-attested obligation ids with matching content fingerprints in the current uncompacted context. Receipts stay in the matching RAM cursor chain; omission, drift, compaction, handoff, expiry or restart re-delivers. A host may vary the page-local procedural budget so later pages reclaim space no longer occupied by first-page route/project metadata, but every complete response still obeys the same outer envelope. An accepted optional root and its exclusive dependencies remain `accepted`, never synthetic required obligations. Notices may recover an abandoned chain but cannot deliver missing context.

Compact bootstrap metadata must not starve its own paginated units. Selected project/context-message content remains visible with owner/provenance/freshness, while repetitive selector decisions are represented by bounded counts. In compact mode the outer envelope constrains its project and message sub-budgets; independent defaults are not additive entitlements. Optional host diagnostics such as `bridgeTiming` are best-effort envelope metadata: preserve the richest representation that fits, compact it when needed, and omit it before rejecting an otherwise valid bounded core response. A workflow guide too large for the inline allowance is not dropped: its exact `workflow_guide_load` becomes a post-context lifecycle obligation and must run before dependent phase work. Increasing the envelope or silently omitting selected obligations is not a substitute for this separation. The MSSR 0.2.55 adoption adds the corresponding source-side invariant: a compact `SKILL.md` is insufficient if a generic signal selects one monolithic reference, so reusable pattern catalogs need bounded semantic units and conjunctive selectors. MSSR 0.2.56 makes a Context Message's serialized form the minimum selection charge, while 0.2.57 makes cursor identity independent of page-local budget. Bridge keeps piggyback notices concise and drains only a bounded batch, leaving the rest queued with `remainingPending` instead of duplicating an unbounded backlog into one response.

## MSSR host inheritance and skill recipe boundary

Bridge is a host adapter, not a second owner of MSSR skill-selection semantics. Stateful hosts inherit the portable MSSR contract: required roots are obligations; optional roots require an explicit `accepted` decision in `host-gated` mode; explicit `skipped` decisions are observable; an absent decision remains `pending` and must not be rewritten as a synthetic skip. `SKILL.md` remains the routed capability/control plane while `references/` are parent-owned situational recipes selected by `context-modules.json`; creating a new skill requires independent activation, outcome, owner and verification.

Paged context has two separate completion facts. `status=complete` proves only that the selected bounded page chain was delivered; it does not prove the model applied that guidance, completed the phase, passed verification/persistence, or achieved the task. Bridge therefore returns an explicit lifecycle gate with no automatic checkpoint/outcome and requires the same trace to proceed through real work, checkpoint, replan and truthful close. Likewise a Context Plane persistence proposal is only a review queue item: packaged MSSR classifies evidence freshness/conflict, while the canonical owner and normal authorization decide any later write.

## Workflow-guide recommendation specificity boundary

Bridge workflow-guide discovery is a host convenience layer and must not override portable MSSR intent semantics with broad lexical coincidences. When the task is explicitly diagnosing skill/workflow routing, recommendation or coverage, capability names quoted as false-positive/false-negative examples are evidence about the matcher, not intent to execute those capabilities: existing-skill coverage removes known skill-name evidence and suppresses ownership-specific intent boosts, and the guide recommender must remain neutral instead of assigning another owner from those examples. Outside that diagnostic mode, true specialist requests keep normal positive coverage, including explicit Figma, Roblox placement and Roblox save/recovery tasks. Reusable guides should still advertise the architecture vocabulary that actually defines their workflow (`modularization`, `Functional Core`, `Imperative Shell`, ownership boundaries). A live route is accepted only when portable MSSR selects the appropriate capability set and the host guide layer adds procedural guidance without unrelated specialist ownership.
