# Bridge Operational Notice and Situation Model historical boundaries

## Operational notice host decision

Bridge owns one general operational notice transport only: `bridgeNotices`. Portable MSSR decides whether bounded evidence crosses an attention transition; Bridge maps that candidate to queue/TTL/history/automatic MCP-response delivery and may attach bounded preflight/recovery actions. C2b owns routing-compliance semantics over required route/trace/skill/phase obligations. C2c owns explicit consistency diagnosis under semantic claim keys and independent observer role/authority/state/value/revision/boundary. C2d is a separate portable recommendation owner: its evidence-first plan ranks `ready`/`deferred` actions using hard source-of-truth/dependency gates before confidence, expected information gain, risk, reversibility, cost, blast radius and a transparent score. Bridge must render immediate notice actions only from C2d `ready` recommendations; deferred recommendations remain bounded evidence and cannot be promoted by host convenience. Thus known stale generated bytes can block downstream runtime verification until the upstream layer changes, while unresolved canonical/source evidence prioritizes inspection over mutation. Freshness and current consistency remain orthogonal; free-form project memory is never heuristically rewritten. No mismatch or recommendation score authorizes a write/build/install/restart, and future learned recommendation weights remain observe/shadow-only behind replay/calibration/feature-flag/rollback gates.

## C2e Situation Model watcher boundary

Project knowledge is part of operational context, but Bridge must not treat documents as truth merely because they exist. Packaged MSSR 0.2.26 compares bounded revision/claim evidence while preserving owner and evidence-class metadata. Bridge's Project Situation watcher uses durable Context Plane delivery receipts to know which revision was actually delivered to an agent, compares only operationally active receipts with current canonical repository revisions, and persists metadata-only transition state. Newer/current delivery supersedes older receipts, so reloading current context can resolve the alert. The watcher classifies attention (`noticeClass`, project category, bounded priority) but reuses the existing Operational Notice levels/queue; C2d controls ready/deferred ordering. Free-form memory interpretation, learned priors, notice priority and confidence cannot become canonical authority or autoexecute maintenance.

## MssrNotice relay boundary

Bridge Gate E3 adopts packaged MSSR 0.2.31 without creating a second semantic notice system. A genuine portable `MssrNotice v1` is validated and carried unchanged as `BridgeNotice.mssrNotice`; Bridge may mirror semantic fields for compatibility/UI and may add host-only queue ids, timestamps, TTL, occurrences, bounded observation details and suggested actions outside that object. The existing `bridgeNotices` queue/history/automatic-drain path remains the only general Bridge transport. `MssrNotice.noticeId` is semantic lifecycle identity and must not be replaced by the Bridge queue `id`; semantic equality is evaluated on the portable payload, not on the host wrapper. Native Bridge or foreign MCP notices remain source-attributed host/foreign notices with no `mssrNotice` payload and must never be normalized or relabeled as MSSR merely to fit delivery.
