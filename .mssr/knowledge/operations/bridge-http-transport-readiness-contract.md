# Bridge HTTP readiness, storage bootstrap and restart recovery contract

Readiness recovery distinguishes process death from temporary starvation. If the HTTP child has exited, recovery is immediate. If the process is still alive, consecutive readiness failures are only attention evidence: the watchdog must also observe sustained unreadiness for the configured alive-process grace window (90 seconds by default) before terminating the child. Before that kill, it captures a bounded `/status` snapshot with boot id, event-loop diagnostics, HTTP client-error counters, session lifecycle, failure age, and grace duration. A short event-loop stall may delay service, but it must not by itself create a restart/502 cascade for concurrent clients.

Observability schema bootstrap runs in a short-lived child after HTTP listen, so cold SQLite setup does not block the event loop or liveness probes. While storage is initializing, `/readyz` stays responsive and database-backed HTTP routes plus MCP dispatch wait for the shared bootstrap result. A recognized transient SQLite busy/locked failure receives one bounded retry; persistent initialization failure reports live health but revokes readiness and fails database/MCP dispatch closed with 503. A persisted last-good dashboard snapshot remains readable during initialization or failure.

A planned `bridge_request_restart` returns the existing notice with wait-for-readiness guidance; the external watchdog performs the restart. With a caller progress token, Bridge attempts `notifications/progress` before creating the watchdog request, capped at 300 ms. Failure or timeout does not block the request. Transport acceptance does not prove client display/receipt, and Bridge cannot push to unrelated web chats.
