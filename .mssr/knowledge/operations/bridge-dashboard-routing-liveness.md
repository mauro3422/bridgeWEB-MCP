# Bridge dashboard, routing latency, and WAL liveness boundary

## Dashboard work must not define transport health

Bridge liveness and MCP share one HTTP event loop, so synchronous dashboard aggregation can make a healthy process appear dead. On 2026-09-15, a dashboard refresh fanned out across twelve endpoints, duplicated a full metrics profile scan, serialized a multi-megabyte MSSR learning projection, and delayed `/healthz` beyond the watchdog's three-second probe. Three aligned misses caused the watchdog to terminate and recreate an otherwise live HTTP child while the tunnel remained healthy. Dashboard work now belongs in an isolated worker behind one bounded cached snapshot; watchdog timeout remains defense in depth, not a substitute for event-loop isolation. Verification must exercise a cold multi-client snapshot while probing health and prove stable runtime/tunnel identities.

## Routing and catalog latency attribution

Specialized routing latency must be attributed by layer before changing MSSR semantics. A cold Codex skill catalog scan can dominate startup, while the deterministic route, guide ownership and context planner are comparatively small once the catalog is warm. Bridge therefore keeps a watcher-driven in-memory projection of the local Codex catalog: healthy `fs.watch` coverage is the invalidation authority, and the bounded TTL is only a fallback for missing/failed watcher roots. A time-based full rescan must not run merely because 30 seconds elapsed while watcher coverage is healthy. Full `skill_catalog` may expose cache scan/hit/invalidation diagnostics, but compact routing/bootstrap payloads must omit them so observability cannot steal required context-envelope budget. MSSR remains the semantic routing owner.

## Observability durability and WAL maintenance boundary

Observability durability and immediate evidence are separate contracts. Request-path writers enqueue bounded JSONL/SQLite work to the shared single-writer persistence worker instead of blocking the HTTP/MCP event loop; a bounded in-memory overlay provides read-your-writes for live projections while durable persistence catches up. Every projection that promises immediate state (`trace`, `recent`, routing profiles/coverage) must merge persisted rows with pending overlay evidence using stable event-id dedupe plus the domain's ordering/chain semantics; waiting synchronously for SQLite would defeat the liveness fix. Aggregate projections must also reconcile SQLite and the overlay from one bounded read snapshot: a persistence commit may become visible before its acknowledgement removes the same event from RAM, so independently timed aggregate and dedupe reads can transiently double-count or omit one call. SQLite WAL housekeeping remains separate again: writers disable `wal_autocheckpoint`, a worker runs `wal_checkpoint(PASSIVE)` after a true quiet-period debounce, and new writes during a checkpoint schedule another pass only after completion plus a fresh idle period. A slow routing call should be diagnosed by layer—catalog discovery, deterministic MSSR routing/context, Bridge dispatch, persistence/WAL contention, or external ingress/egress—rather than attributed wholesale to MSSR. Transport/readiness/routing-latency alerts are Bridge-native Notice concerns; portable MSSR notices remain semantic/project-maintenance evidence.
