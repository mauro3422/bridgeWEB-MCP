# Bridge project memory

## Resumable skill-context invariant

`maxContextChars` bounds selected procedural text while `maxEnvelopeChars` bounds the complete compact response (32.000 by default); neither may be inferred from the other. When selected context does not fit, `skill_bootstrap`/`skill_context_next` must expose a deterministic partial chain and the caller must reach `status=complete` before dependent work. Opaque cursors contain no prompt, transcript or procedural content, are valid only against the same trace/live selected bytes and order, and are kept only as a fingerprinted RAM continuation lease. A host may vary the page-local procedural budget so later pages reclaim space no longer occupied by first-page route/project metadata, but every complete response still obeys the same outer envelope. An accepted optional root and its exclusive dependencies remain `accepted`, never synthetic required obligations. Notices may recover an abandoned chain but cannot deliver missing context.

Compact bootstrap metadata must not starve its own paginated units. Selected project/context-message content remains visible with owner/provenance/freshness, while repetitive selector decisions are represented by bounded counts. In compact mode the outer envelope constrains its project and message sub-budgets; independent defaults are not additive entitlements. A workflow guide too large for the inline allowance is not dropped: its exact `workflow_guide_load` becomes a post-context lifecycle obligation and must run before dependent phase work. Increasing the envelope or silently omitting selected obligations is not a substitute for this separation. The MSSR 0.2.55 adoption adds the corresponding source-side invariant: a compact `SKILL.md` is insufficient if a generic signal selects one monolithic reference, so reusable pattern catalogs need bounded semantic units and conjunctive selectors. MSSR 0.2.56 makes a Context Message's serialized form the minimum selection charge, while 0.2.57 makes cursor identity independent of page-local budget. Bridge keeps piggyback notices concise and drains only a bounded batch, leaving the rest queued with `remainingPending` instead of duplicating an unbounded backlog into one response.

## MSSR Context Plane ack tombstone semantics

`mssr_context_ack` records delivery receipts only in canonical ephemeral `.mssr/runtime/context-inbox.json`. MSSR 0.2.18 never reads `.bridge/mssr-context-inbox.json` as live state; explicit project initialization may remove that known obsolete artifact only after canonical project control is valid. Ack suppresses identical evidence only: same id/content fingerprint remains suppressed, while a changed source revision/content must reappear. Pending messages follow the same subject-vs-content distinction: same subject plus identical fingerprint deduplicates; a newer revision replaces the older pending item. Bridge owns host delivery/runtime integration and must not widen suppression or reinterpret receipts as project truth. Separately, Godot scene lifecycle work now has a native no-click boundary: opening or creating scenes must use provider/editor operations (`open_in_godot`, `create_scene`, `read_scene`, `scene_tree_dump`) through dedicated Bridge tools, reuse the connected intended editor, and treat persistence, editor state, visual review, and runtime behavior as separate evidence layers. The Godot provider may host multiple editor projects concurrently; mutating scene operations must therefore select an exact `projectPath`, `projectId`, or `editorInstanceId` whenever more than one editor is connected, and Bridge must fail closed rather than defaulting to the first editor.

## MSSR host inheritance and skill recipe boundary

Bridge is a host adapter, not a second owner of MSSR skill-selection semantics. Stateful hosts inherit the portable MSSR contract: required roots are obligations; optional roots require an explicit `accepted` decision in `host-gated` mode; explicit `skipped` decisions are observable; an absent decision remains `pending` and must not be rewritten as a synthetic skip. `SKILL.md` remains the routed capability/control plane while `references/` are parent-owned situational recipes selected by `context-modules.json`; creating a new skill requires independent activation, outcome, owner and verification.

Paged context has two separate completion facts. `status=complete` proves only that the selected bounded page chain was delivered; it does not prove the model applied that guidance, completed the phase, passed verification/persistence, or achieved the task. Bridge therefore returns an explicit lifecycle gate with no automatic checkpoint/outcome and requires the same trace to proceed through real work, checkpoint, replan and truthful close. Likewise a Context Plane persistence proposal is only a review queue item: packaged MSSR classifies evidence freshness/conflict, while the canonical owner and normal authorization decide any later write.
## Workflow-guide recommendation specificity boundary

Bridge workflow-guide discovery is a host convenience layer and must not override portable MSSR intent semantics with broad lexical coincidences. When the task is explicitly diagnosing skill/workflow routing, recommendation or coverage, capability names quoted as false-positive/false-negative examples are evidence about the matcher, not intent to execute those capabilities: existing-skill coverage removes known skill-name evidence and suppresses ownership-specific intent boosts, and the guide recommender must remain neutral instead of assigning another owner from those examples. Outside that diagnostic mode, true specialist requests keep normal positive coverage, including explicit Figma, Roblox placement and Roblox save/recovery tasks. Reusable guides should still advertise the architecture vocabulary that actually defines their workflow (`modularization`, `Functional Core`, `Imperative Shell`, ownership boundaries). A live route is accepted only when portable MSSR selects the appropriate capability set and the host guide layer adds procedural guidance without unrelated specialist ownership.

## Daily structural Skill Health boundary

Bridge may automatically run the structural skill audit once per day and persist only privacy-safe metadata needed for trends: names/sources, line/character counts, manifest/module counts, reference counts/sizes, advisory status/reason codes and deltas. The audit is read-only and advisory: `WATCH`/`REVIEW`, growth, full fallback or unindexed recipes may recommend human maintenance but never authorize automatic edits, routing changes, skill splitting or deletion. Procedural skill/reference content, prompts and transcripts are excluded from the store.
## Privileged Windows operations boundary

Generic shell tools must remain non-elevated and keep their dangerous-command blacklist. When a legitimate local maintenance task needs Windows administrator rights, expose a dedicated tool with a closed semantic profile instead of accepting an arbitrary command or arbitrary target path. The dedicated tool must default to inspection/dry-run when practical, resolve and revalidate its target internally, use a visible UAC elevation boundary, emit an auditable result, and post-verify the observable target state. The first implementation is the `amd-dxc-cache` profile behind `windows_admin_cache_status` / `windows_admin_cache_cleanup`; adding another privileged target requires an explicit new approved profile and regression coverage.

## Privileged Windows storage diagnostics
Privileged Windows disk diagnostics must remain fixed-capability operations, not generic elevated shells. Bridge 0.6.95 adds `windows_admin_storage_audit`, a no-argument read-only UAC tool that reports pagefile allocation, VSS shadow storage, Reserved Storage/storage-reserve quotas, Windows RE placement, and bounded protected-directory summaries. During the 2026-08-15 C: audit, VSS used 0 bytes with no shadows, Windows RE was located on the separate recovery partition, and `fsutil storagereserve query C:` reported 6,711 MB of guaranteed reserve across active reserve IDs. Generic `run_command` privilege restrictions remain unchanged.

## Privileged Windows cache cleanup profiles
Protected Windows cleanup remains a closed, profile-scoped capability rather than generic elevated shell access. `windows_admin_cache_cleanup` accepts only approved enum profiles. As of Bridge 0.6.96: `windows-update-download` targets only `%WINDIR%\SoftwareDistribution\Download`, records `wuauserv`/`BITS` state, stops them only when needed, and restores the prior running state; `edgecore-stale` targets only `%ProgramFiles(x86)%\Microsoft\EdgeCore`, derives the installed Edge version from `msedge.exe`, preserves that version plus non-version directories such as `Optimized`, and removes only older numeric EdgeCore directories. Edge WebView2 is deliberately outside this cleanup boundary because multiple WebView2 versions can be concurrently active for Windows Widgets, WhatsApp, or other applications. Always inspect active process executable paths before pruning versioned runtimes. Cache-status scans are recursive and skip symbolic links; physical free-space delta remains the authoritative reclaim measurement when hardlinks/reused files make logical byte totals misleading.

## Packaged dependency byte-parity invariant

A local `file:` npm dependency is not considered adopted merely because `npm install` reports `up to date`. Replacing a tarball under the same version/path can leave stale package bytes in npm cache or `node_modules`. For Bridge releases that consume a rebuilt MSSR artifact, verify source tarball = vendor tarball and compare SHA-256 of critical source/installed runtime files; if parity fails, reinstall through a clean bounded cache or bump the package version before trusting tests/live adoption. Package-manager status is convenience evidence, not the source of truth for runtime bytes.


## Executable release parity invariant

Before a restart is considered an adoption attempt, the package version, source runtime version, compiled executable (`dist/config.js` or equivalent), and packaged dependency bytes must agree. A source/package preflight that ignores `dist/` can pass while the watchdog correctly relaunches stale code. After any late source-version edit, rebuild before restart and read back both compiled and live versions. A watchdog ack proves restart execution, not adoption of the intended bytes. The 0.6.102 C2b adoption demonstrated this directly: the first restart ack succeeded but relaunched compiled 0.6.101; only after rebuilding and proving `package=source=dist=0.6.102` did the next restart adopt the intended runtime.
## HTTP test health-store isolation invariant

Any test that launches `dist/http.js` must isolate **all** host-owned observability stores from live `data/`, not only metrics/logs: Skill Health, Project Context Health, Runtime Health, and Project Situation must point at temporary test paths, and Project Health/Project Situation must use explicit bounded test roots. The top-level isolated regression runner sets these paths, but standalone HTTP fixtures must also set them so direct test execution cannot pollute production observability. After changing scheduler/store plumbing, verify live-store boot/snapshot identity before and after focused tests; test-generated runtime or Situation evidence in live stores is a regression, not harmless telemetry.

## HTTP child readiness and lost-response evidence invariant

Tests that spawn `dist/http.js` and live smokes that follow a build/watchdog transition must treat endpoint availability as a bounded readiness condition, not assume a successful earlier request guarantees the next one. Poll boundedly, and distinguish temporary connection refusal from an exited child; if the child exits, fail with its exit code and captured output. Likewise, a lost MCP/connector response, 502, timeout, or `request terminated without response` does not prove the underlying local operation failed. Before retrying a potentially duplicative operation, inspect Bridge metrics, terminal/process state, or another authoritative receipt for the original call's completion and exit/result status.

## Operational notice host decision

Bridge owns one general operational notice transport only: `bridgeNotices`. Portable MSSR decides whether bounded evidence crosses an attention transition; Bridge maps that candidate to queue/TTL/history/automatic MCP-response delivery and may attach bounded preflight/recovery actions. C2b owns routing-compliance semantics over required route/trace/skill/phase obligations. C2c owns explicit consistency diagnosis under semantic claim keys and independent observer role/authority/state/value/revision/boundary. C2d is a separate portable recommendation owner: its evidence-first plan ranks `ready`/`deferred` actions using hard source-of-truth/dependency gates before confidence, expected information gain, risk, reversibility, cost, blast radius and a transparent score. Bridge must render immediate notice actions only from C2d `ready` recommendations; deferred recommendations remain bounded evidence and cannot be promoted by host convenience. Thus known stale generated bytes can block downstream runtime verification until the upstream layer changes, while unresolved canonical/source evidence prioritizes inspection over mutation. Freshness and current consistency remain orthogonal; free-form project memory is never heuristically rewritten. No mismatch or recommendation score authorizes a write/build/install/restart, and future learned recommendation weights remain observe/shadow-only behind replay/calibration/feature-flag/rollback gates.

## C2e Situation Model watcher boundary

Project knowledge is part of operational context, but Bridge must not treat documents as truth merely because they exist. Packaged MSSR 0.2.26 compares bounded revision/claim evidence while preserving owner and evidence-class metadata. Bridge's Project Situation watcher uses durable Context Plane delivery receipts to know which revision was actually delivered to an agent, compares only operationally active receipts with current canonical repository revisions, and persists metadata-only transition state. Newer/current delivery supersedes older receipts, so reloading current context can resolve the alert. The watcher classifies attention (`noticeClass`, project category, bounded priority) but reuses the existing Operational Notice levels/queue; C2d controls ready/deferred ordering. Free-form memory interpretation, learned priors, notice priority and confidence cannot become canonical authority or autoexecute maintenance.

## MssrNotice relay boundary

Bridge Gate E3 adopts packaged MSSR 0.2.31 without creating a second semantic notice system. A genuine portable `MssrNotice v1` is validated and carried unchanged as `BridgeNotice.mssrNotice`; Bridge may mirror semantic fields for compatibility/UI and may add host-only queue ids, timestamps, TTL, occurrences, bounded observation details and suggested actions outside that object. The existing `bridgeNotices` queue/history/automatic-drain path remains the only general Bridge transport. `MssrNotice.noticeId` is semantic lifecycle identity and must not be replaced by the Bridge queue `id`; semantic equality is evaluated on the portable payload, not on the host wrapper. Native Bridge or foreign MCP notices remain source-attributed host/foreign notices with no `mssrNotice` payload and must never be normalized or relabeled as MSSR merely to fit delivery.
