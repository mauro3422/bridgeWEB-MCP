# multiplayer-gate

## Goal

Use MP only for authority/network/cross-client behavior.

## Instructions

After SP passes, use one dedicated server and two isolated clients only when required. Never substitute a second server for the second player.

Before launching the second client, normalize both client cachedirs to the same low-RAM test profile unless visual fidelity is itself under test. Prefer a reusable project launcher over ad-hoc commands. Keep the two clients symmetric: same heap cap, resolution/FPS class, `-nosteam`, `-nosound`, `-novoip`, and the same canonical local mod payload. For MauroPrime, start from roughly 800x600, 30 FPS, compressed/simplified textures, high-resolution placed items disabled and a bounded client heap; preserve only the interactions the test needs (movement, inventory, timed actions, clothing/equipment and the feature UI). On B42.20.3, both `-Xmx1200m` and `-Xmx1500m` were proven too low by Java-heap OOMs during/after world load. Use `-Xmx1800m` as the current low-RAM floor for these MP clients until a later runtime is explicitly proven lower, while keeping the symmetric 800x600/minimal-graphics profile.

Measure host available RAM before client A, before client B, and after B reaches the world. If memory falls into a dangerous floor, protect the human-controlled session rather than forcing the replay: stop only the disposable peer, lower the symmetric client profile, or move server/client load to another machine when that machine actually has the graphical client installed.

Before launching any client after a mod edit, prove client/server payload parity. This is a mandatory pre-launch gate, not a cleanup step: prepare one canonical payload/artifact, deploy that exact payload to the dedicated and every isolated client, verify its hash (or a representative changed-file hash plus exact file count), and only then start/restart the dedicated. Do not launch client A until the restarted server is confirmed ready with that payload. For B42 servers with `DoLuaChecksum`, a stale dedicated payload can leave the client stuck at `DoLuaChecksum` and later trigger `ChecksumUpdate / Lua incorrect checksum`; if parity cannot be proven, stop the loop instead of trying the client anyway.
Before launching client A when the dedicated lives on another machine, prove the remote test node itself is reachable first. Require the configured/pinned SSH identity to resolve, a successful bounded SSH probe, and the dedicated game port to be listening after `SERVER STARTED`. If the remote host disappears, changes network, suspends, or cannot be rediscovered by its pinned identity, abort the client launch and free any disposable local client instead of diagnosing the resulting connection screen as a mod failure. Remote-node liveness is a prerequisite for payload parity and server-readiness evidence, not something to infer after a failed client connection.

For disposable MP bug-testing actors, remove survival noise from the test without mutating player permission/mode flags from Lua. When the feature under test is networking/UI/equipment rather than health, spawn/restore the fixture healthy and apply protection through the dedicated server's native admin console after the actor is materialized. In B42.20.3, `help godmodeplayer` confirms `godmodeplayer "username" -true/-false` is an explicit server-side setter for invincibility, and `help additem` confirms `additem "username" Base.Item count` for test inventory. Prefer these native commands for laboratory privileges/items. Do not call `setGodMod`, `setInvincible`, `setGhostMode`, or similar permission/mode setters from a client/server test mod: doing so triggered `AntiCheatPermission` with `PlayerPacketReliable: invalid mode` and kicked the client. The earlier observation where `godmodeplayer ... -true` appeared to disable Pingu occurred while a Lua harness was concurrently reasserting mode state; do not treat that race as command semantics. Never ship test immortality/admin helpers in the production mod. If a fixture dies before native protection is applied, stop the dedicated cleanly, restore only that known-good player fixture from backup, verify `isDead=0`, restart, materialize the player, then apply the native server command before destructive replay steps.

Treat the dedicated-server `players` command (or an equivalent authoritative server roster) as the primary proof that a client socket/user is connected, but do not confuse that with a fully materialized/playable client. Require a real client-world signal such as an `OnPlayerUpdate(player)` callback for the materialized actor, `GAME_START`, a `WORLD_HEARTBEAT` based on `getPlayer() + getCurrentSquare()`, or direct human confirmation before declaring the client ready. Apply native admin-console protection only after that materialization gate so the dedicated command targets the real world player object. Never infer readiness from a screenshot of the loading screen, a stale `Waiting for player-connect response` line, or process liveness alone.

Launch sequentially: A first, then wait for both server presence and a real playable/world signal from A. Only then launch B. If A is still at checksum/loading, do not open B and double memory pressure. After B launches, apply the same readiness rule before interpreting marker/network results.

Keep roles explicit. The human-controlled client under test must remain observational/manual unless the current test explicitly authorizes automation: do not auto-wear/unequip watches, open maps, change channels or mutate inventory merely to make the harness convenient. A disposable peer may auto-provision the minimum stable fixture needed to remain visible. Record which side is manual versus synthetic before interpreting results.
